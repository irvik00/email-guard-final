## Этап 2. Три модели и одинаковая кросс-валидация

У всех вариантов вход model_text. Выход — оценка класса spam=1.
Векторизатор и классификатор объединяются в sklearn Pipeline. Fit словаря,
IDF и параметров модели идёт только на обучающей части каждого фолда;
transform на его проверочной части. Нельзя заранее fit_transform всего train
и потом делить готовую матрицу для CV.

Три заранее заданных варианта, без большого поиска гиперпараметров:

| ID | Текстовые признаки | Модель |
|---|---|---|
| word_nb | TF-IDF слова и пары слов (1,2) | MultinomialNB, alpha=1.0 |
| word_lr | Такой же TF-IDF | LogisticRegression, C=1.0 |
| char_lr | TF-IDF символьных фрагментов char_wb (3,5) | LogisticRegression, C=1.0 |

Общие параметры TF-IDF: lowercase=True, sublinear_tf=True, norm=l2,
stop_words=None; word min_df=2, max_features=80000;
char min_df=3, max_features=150000. Не лемматизировать и не переводить.
Lowercase — явное преобразование этого эксперимента, не переписывание оригиналов.
Char_wb фрагменты помогают сравнить представления; устойчивость к обходам
или мультиязычность без проверок не заявлять.
Для LR: L2-регуляризация, подходящий установленной версии solver для sparse
binary classification, например liblinear, max_iter=2000, random_state=42,
class_weight=None. Зафиксируй окончательный полный get_params.
При ConvergenceWarning не скрывай его: увеличь лимит при том же эксперименте
и запиши изменение. Другие настройки не меняй, чтобы «догнать F1».

Используй один и тот же сохранённый mapping из 5 train-CV фолдов manifest.
Проверь охват, группы и оба класса в каждом фолде. Если mapping не читается
из фактической схемы, адаптируй загрузчик, не создавай другие фолды молча.
Если mapping отсутствует, создай и сохрани единый StratifiedGroupKFold
5/shuffle=True/seed=42 только на train; это отдельное документированное решение.
Сначала проведи CV каждого Pipeline, сохрани OOF-оценки с ID/группой/источником.
Каждая train-запись получает одну OOF-оценку от модели, её не обучавшей.

Порог сравнения моделей заранее фиксирован 0.5 для всех.
Выбор baseline: максимальное среднее binary F1 по фолдам для spam=1;
при численном равенстве — выше средняя precision, затем word_lr, char_lr, word_nb.
Значения OOF/среднее по фолдам — оценка для выбора, не независимый финальный тест.
Одинаковые фолды обязательны для честного сравнения.

CPU, sparse-матрицы без toarray для корпуса. Модели/фолды можно выполнять
последовательно, чтобы не создавать много копий матриц. Логи времени,
числа признаков и предупреждений; никаких полных текстов в терминале.
Не запускай бесконечный grid search. При ограничении ресурсов опиши изменение
лимита признаков как новый вариант и не сравнивай разные настройки под одним ID.

## Этап 3. Валидация и порог

После CV fit каждый вариант на полном train и предскажи validation.
Предварительно выбранный по CV baseline не меняй по validation-таблице;
если порядок отличается — сообщи это как наблюдение для следующего дня.

Для каждого варианта сохрани binary precision/recall/F1 (positive=spam),
accuracy как дополнительную метрику, TP/FP/TN/FN, FPR=FP/(FP+TN), поддержку
классов. Для source-разреза посчитай те же показатели на validation отдельно
для SpamAssassin и Ling-Spam. При нулевом знаменателе укажи undefined и support,
а не выдуманную идеальную оценку. Явно задай zero_division и семантику отчёта.
Добавь DummyClassifier(strategy=most_frequent) для ориентира на validation
без CV-поиска; это контроль, а не четвёртая обученная текстовая модель.

Для выбранного baseline сравни на validation три режима:
1. Порог 0.5 — исходный.
2. Порог с максимальным validation binary F1 — исследовательский.
3. Максимальный validation binary F1 при наблюдаемом FPR <=1% — осторожный.

1% — предварительный инженерный сценарий, не утверждённый бизнес-SLA и
не гарантия FP в реальной почте. Для режимов 2/3 используй сетку уникальных
validation-оценок, include 0.5 и вариант выше максимальной оценки для «ни одного
положительного»; предсказание score>=threshold. Tie-break: меньше FP, затем
больше recall, затем больший threshold. Если режим 3 даёт нулевой recall или
все отрицательные — честно сообщи, не называй это хорошим рабочим вариантом.
При отсутствии содержательного результата не ослабляй 1% автоматически.

Предложи режим 3 как provisional operating point, если recall>0;
иначе оставь provisional 0.5 с явным unmet_fp_scenario. Сохрани отдельно
threshold_default, threshold_f1, threshold_conservative и выбранную политику.
Порог подбирается по validation только у заранее выбранной модели.
Validation-метрики после подбора порога оптимистичны; финальный test закрыт.
Не утверждай F1>=0.86 как выполненное требование курса по validation.

Для recall (знаменатель TP+FN) и FPR (FP+TN) выбранного baseline добавь
95% Wilson interval и исходные числитель/знаменатель для каждого режима.
Это интервал наблюдаемой доли при предпосылках биномиальной модели, не защита
от дрейфа/ошибочных меток/зависимости кампаний. Не называй его CI для F1.
Если умеешь посчитать групповой bootstrap F1 — сегодня не нужно: он не обязателен.

Оценки predict_proba — модельные оценки, не доказанная калибровка вероятностей
отдельного письма. В UI/CLI назвать spam_score, не «гарантированная вероятность».

## Этап 4. Анализ ошибок и объяснение

Только validation выбранного baseline: до 5 FP и 5 FN при provisional threshold,
несколько правильных примеров; если ошибок меньше — все, не придумывай.
Для анализа достаточно ID, source, метки, score, порога, короткого обезвреженного
фрагмента и наблюдения. Не переписывай метки и не меняй модель по этим примерам
в текущем запуске. Список улучшений отдельно для дня 4, без применения к test.

Для LR сохрани глобальные признаки с положительными/отрицательными весами.
Локальное объяснение: вклад x_j*w_j присутствующих признаков в logit spam,
intercept отдельно; сумма вкладов всех активных признаков + intercept должна
совпадать с decision_function в допуске. Top-N — неполная часть суммы,
не сумма вероятностей и не доказательство причинности. Для char покажи
фрагменты с явными границами/экранированием, а не выдавай их за слова.
Если baseline NB, можно показать различие feature_log_prob_ классов и вклад
x_j*(logP_j_spam-logP_j_ham) плюс разность class_log_prior_. Это фактическое
объяснение логарифмического отношения оценок NB, не размышления модели.
Проверь классы_/направление знака. Не используй LLM для выдуманных объяснений.

Замечай тематические подсказки корпуса, малое пересечение словаря, форматный
шум и недостаток контекста как гипотезы, не как доказанные причины каждого FP.
Контакты/URL скрывай только в приватном отчёте, не изменяй обучающие данные.

## Этап 5. Сохранение и проверка применения

Сохрани три fit-на-train Pipeline и выбранный baseline в models/day3/
с воспроизводимым manifest. Удобно joblib собственных локальных артефактов.
Не загружай чужие pickle/joblib из датасетов. Bundle должен содержать или
ссылаться на threshold config, classes, версии, параметры model_text builder,
хеши входов/config и признаки. Не сохраняй только коэффициенты без TF-IDF.
Для test/validation правила подготовки текста те же, что для новых писем.

CLI для одного .eml: существующий парсер → ровно тот же builder model_text
→ transform/predict без fit → spam_score и binary verdict при заданном пороге.
Не подключай заголовки/URL-метаданные как признаки, если модель на них не училась.
Фишинг и category вернуть not_available, не придумывать их по binary output.
Пока английский исторический baseline: незнакомый язык/нулевая векторизация
помечаются ограничением; не обещай поддержку русского или 15 языков.
Можешь добавить diagnostics для empty_vector без скрытой подмены предсказания.

Проверь save/reload: оценки на небольшой validation-подвыборке совпадают
до/после сохранения в допуске. Проверь CLI на искусственном .eml из учебных
examples/fixtures, не на закрытом тесте и не на заблокированных архивах.
Входные файлы/содержимое модели не должны меняться при обычном predict.
Не «пересоздавай» учебные примеры под желаемые результаты; это демонстрация,
не измерение качества. Не делать fine-tune/добавление примеров по её ответу.
